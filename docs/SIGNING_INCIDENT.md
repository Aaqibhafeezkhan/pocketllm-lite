# Signing-key incident assessment

Assessed 2026-10-15 (pass 3). Method: public, non-secret evidence only. No key
material, password or keystore contents were read, printed or copied; the two
credential-looking files were treated as opaque by path and commit metadata.
Nothing was rotated, deleted or rewritten.

## 1. Question

Pass 2 found `upload-keystore.jks` and `android/key.properties.bak` in the
public history of `origin/main`. Did any distributed APK use that identity, and
what must be done?

## 2. Evidence

### 2.1 Repository

| Fact | Evidence |
| --- | --- |
| `upload-keystore.jks` was added 2025-12-29 (`c82e363`), "removed" 2026-01-18 (`a3e9602`), with a revert and re-removal in between (`853ca92`, `d5b5f6c`) | `git log --all -- upload-keystore.jks` |
| It remains reachable in public history of `origin/main` | `git log origin/main -- upload-keystore.jks` |
| `android/key.properties.bak` was added in `816e3f8` and tracked until pass 2 | `git ls-files`, `git log` |
| `.gitignore` listed `key.properties` but not `*.bak`, which is why the backup was tracked | `.gitignore` before pass 2 |
| The file contents of both were **not read**: whether real passwords were exposed is unknown | permission denied, by design |

### 2.2 Distributed APKs (public certificate fingerprints)

The signing certificate of the arm64 APK of every release that has one was read
from the APK Signing Block via HTTP range requests (public data):

| Release | Published | Certificate SHA-256 (prefix) | Subject |
| --- | --- | --- | --- |
| v1.0.38, v1.0.37, v1.0.35, v1.0.34, v1.0.33, v1.0.30, v1.0.21, v1.0.20, v1.0.19, v1.0.13 | 2026-05-18 to 2026-08-29 | `f11e976967911c8e…` | `CN=Android Debug, O=Android, C=US` (valid from 2026-05-18) |
| release-v1.0.10 | 2026-02-17 | `f8821bb3139cb34b…` | `CN=Android Debug, O=Android, C=US` (valid from 2025-02-09) |

Findings:

1. **No sampled public release is signed with a non-debug identity.** Both
   certificates are Android *debug* certificates, from two different machines.
2. The 2026-02-17 release is signed with a debug key created on 2025-02-09, so it
   was not signed with a keystore generated by the committed `upload-keystore.jks`
   unless that file is itself a debug-style certificate. This cannot be settled
   without comparing fingerprints, which needs the keystore: see action M1.
3. The signer already changed once (v1.0.10 to v1.0.13). Users upgrading across
   that boundary could not update in place. This is precedent, not new risk.
4. Only the arm64 APK of each release was sampled. Other ABIs and the universal
   APK of the same build normally share the signer but were not each verified.
5. The app is not listed at `play.google.com/store/apps/details?id=com.pocketllm.pocketllm_lite`
   (HTTP 404 on 2026-10-15), so Google Play App Signing does not currently apply.

### 2.3 What the debug signature means for users

A debug certificate provides no meaningful publisher identity. Android checks
only that an update matches the installed certificate; anyone holding the
private debug key could sign a malicious update that installs over the app.
That key lives on the maintainer's build machine (default password, per-machine
file). Today, integrity for users rests on the release page, not on the
signature. The `SHA256SUMS.txt` published since v1.0.37 helps only if it is
obtained from a trusted channel.

## 3. Assessment

| Risk | Rating | Reasoning |
| --- | --- | --- |
| The leaked keystore protected a live production identity | **Unknown, probably low** | No release uses a non-debug certificate. It may have been an upload key for a store listing that does not exist |
| The leaked keystore's passwords were exposed | **Unknown** | `key.properties.bak` contents not inspected; assume yes |
| Users can be targeted via the debug key | Low to moderate | Needs theft of the build machine's private debug keystore |
| Users cannot receive in-place upgrades to a production key | **Certain** | Android rejects a signer change without rotation lineage |

Treat `upload-keystore.jks` as compromised regardless. It must never become the
production signing identity.

## 4. What was implemented (safe, local, reversible)

- `android/key.properties.bak` untracked; `key.properties*`, `*.jks`,
  `*.keystore`, `*.p12`, `*.pfx`, `*.bak` ignored.
- `scripts/ci/check-secrets.mjs` (wired into CI): fails on tracked key files,
  keystore magic numbers, PEM private keys, literal signing passwords and common
  token formats. It prints paths and rule names only.
- `test/regressions/no_committed_secrets_test.dart` (Dart-side guard).
- Gradle: `-Prelease.requireSigning=true` refuses the debug fallback; secrets
  come from environment variables or an untracked `key.properties`.
- Release workflow requiring protected secrets and failing on debug signatures;
  `scripts/release/verify-apk-signature.mjs`.

## 5. Migration plan

### 5.1 Create the production identity (maintainer, M2)

On a trusted machine, with a strong passphrase, not in this repository:

```bash
keytool -genkeypair -v -keystore pocketllm-release.p12 -storetype PKCS12 \
  -alias pocketllm -keyalg RSA -keysize 4096 -validity 10950
# record: keytool -list -v -keystore pocketllm-release.p12  (publish SHA-256 only)
```

Keep two offline encrypted backups. Losing the key means no future upgrades.

### 5.2 Secrets and CI (M3)

Add `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
`ANDROID_KEY_PASSWORD` as secrets of a GitHub *environment* named `release` with
required reviewers. The workflow in `.github/workflows/release.yml` already
consumes them and never falls back to the debug key.

### 5.3 Android version compatibility

| Android | Behaviour when the signer changes |
| --- | --- |
| 7.0 to 8.1 (API 24 to 27, this app's minSdk is 24) | No rotation support. Update fails; user must uninstall and reinstall |
| 9.0 and later (API 28+) | APK Signature Scheme v3 rotation lineage is honoured **if** the lineage was created with the old key |

Do not assume rotation works for every supported device.

### 5.4 Existing users (M4)

1. **Always available:** backup, uninstall, reinstall, restore. In the old app
   create a `.pllm` backup (Settings, Chats and Local Data), move it off the
   device, uninstall, install the signed build after verifying its SHA-256 and
   the certificate fingerprint published in `SECURITY.md`, then restore. Models
   are not part of the backup and must be downloaded again. Data does **not**
   survive the reinstall automatically.
2. **Optional, API 28+ only:** create a rotation lineage from the original debug
   keystore (still present on the build machine; its fingerprint matches
   `f11e9769…`) to the new key with `apksigner rotate`, then sign with
   `--lineage`. Test on an API 28+ device and on an API 24 to 27 device before
   announcing. Document that Android 7 and 8 users must use method 1.

State the method honestly in the release notes. Do not describe the first
production-signed APK as an upgrade for everyone.

### 5.5 Google Play (M5, only if publishing there)

Enrol in Play App Signing. Use the *new* key as the upload key, never the
committed one. Play re-signs for users with an app-signing key that Google
holds, which also solves the later-rotation problem.

### 5.6 Repository history (M6, requires coordination)

Options, in order of preference:

1. **Leave history as is.** Acceptable if M1 shows the committed keystore never
   protected a live identity. Rely on "never use this key".
2. **Rewrite history** with `git filter-repo` to drop `upload-keystore.jks` and
   `android/key.properties.bak`, force-push, and ask every collaborator and fork
   owner to re-clone. This breaks open PR refs and does not remove copies
   already cloned or cached; request a cache purge from GitHub Support and
   enable secret scanning with push protection. Do not do this without
   explicit maintainer sign-off and a backup of the repository.
3. Never delete historic releases to hide the signer; document it instead.

### 5.7 Preventing recurrence

Done: ignore rules, CI guard, Dart guard, fail-closed Gradle, protected
workflow. Maintainer: enable GitHub secret scanning and push protection; require
the CI check on `main`; keep keystores only in the password manager and the
protected environment.
